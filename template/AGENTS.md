# 작업 규칙

- 플랫폼 지침(~/.codex/AGENTS.md)과 과제 README가 이 규칙보다 우선이다. 부딪히면 Decision Log에 적는다.
- 사람은 판단·담당자 대화·이해를 맡고, 파일·git·명령은 Codex가 맡는다. 막히면 원인 1줄과 필요한 승인을 말한다.

## 지켜야 할 선 (작업 폴더가 홈이면 실수 하나가 홈 전체에 미친다)
- 홈 설정(~/.codex · ~/.bashrc · ~/.profile · ~/.config · ~/.npmrc 등)과 샌드박스·승인·네트워크·패키지 설정(레지스트리·프록시)은 고치지 않는다. 막히면 우회하지 말고 원인 1줄과 필요한 승인을 말한다.
- 점(.)으로 시작하는 홈 폴더·파일은 열지도 고치지도 않는다. 예외: .gitignore · .env.example · .kit/
- 샌드박스 밖 실행 승인은 이번 한 번만 요청한다. "다시 묻지 않기" 규칙(prefix_rule)은 붙이지 않는다(~/.codex에 저장된다).
- git 쓰기는 `add <경로>` · `commit` · `tag <새 이름>`만 쓴다. `add .` · `add -A` · `add -u` · `commit -a` · clean · reset · checkout/restore로 되돌리기 · stash · rebase · amend · `tag -f` · push · remote · config · .git 삭제는 하지 않는다. 필요해 보이면 이유를 말하고 묻는다.

## 기록은 PLAN.md 한 곳
- 계획·설계·진행·결정·발견·약점·담당자 대화는 PLAN.md에만 쓴다. 코드 주석·커밋·보고에서는 번호(R1·Q1·D-1)로 가리키고 다시 풀어 쓰지 않는다.
- 예외: README가 요구한 제출 문서는 읽는 사람을 위한 문장으로 쓰고, 내용은 PLAN.md에서 가져온다.
- 제목에 "덧붙이기만"이 있는 절은 지난 줄을 고치지 않고 아래에 덧붙인다. ▶ 두 줄과 나머지 절은 항상 최신으로 고친다.
- 결정·발견은 나온 즉시 적는다(세션은 언제든 끊긴다). 5절은 약속어 하나에 1줄, 7절은 같은 사실을 다시 적지 않는다. 시각은 `TZ=KST-9 date +%H:%M`로 얻는다.
- PLAN.md는 필요한 절만 읽는다(./scripts/status.sh · `sed -n '/^## 3\./,/^## 4\./p' PLAN.md`). 한 세션에서 통째로 여러 번 읽지 않는다.
- 읽기 전용 세션(보조)은 파일을 쓰지 않고 테스트·서버도 돌리지 않는다(거짓 실패가 난다). 코드·PLAN.md·git으로만 본다.

## 범위
- 요청과 PLAN.md 요구사항 범위 안에서만 바꾼다. 요청하지 않은 기능·파일·리팩토링·방어 코드는 만들지 않는다. 범위 밖 문제는 8절에 1줄.
- README에 없는 결정은 혼자 정하지 않는다. 담당자 질문 후보로 올리고, 답을 받기 전에는 2절 해당 줄에 [가정: …]으로 두고 진행한다. 끝내 정해지지 않는 값은 3절 옵션 표에 기본값과 함께 두고 바꿀 수 있게 만든다.
- 3절 계층 지도에 없는 모듈을 새로 만들거나 계층·구조를 바꿀 때만 먼저 3줄(바꿀 것 / 깨지면 안 되는 것 / 검증 방법)을 말하고 확인을 기다린다.

## 코드
- 계층을 나눈다: 입력·HTTP → 산출 로직 → 저장 → 화면. 산출 로직(계산·판정·검증)은 HTTP·DB·환경변수를 모르는 순수 함수로 두고 단위 테스트한다. 경계는 3절 계층 지도에 파일 경로로 적는다.
- 테스트는 포트를 열지 않는다(샌드박스가 127.0.0.1도 막는다). HTTP 처리도 (요청 → 상태·본문) 함수로 떼어 소켓 없이 부른다. 서버를 띄워 보는 확인은 사람이 한다(띄웠다면 끝에 반드시 끈다).
- 새 함수를 만들기 전에 같은 일을 하는 코드를 검색한다. 이름은 기존 코드와 4절 용어집을 따른다. 이미 설치된 라이브러리를 먼저 쓰고, 새 의존성은 먼저 묻고 이유를 Decision Log에 남긴다.
- 입력은 서버에서 검사한다. 실패는 삼키지 않고 로그로 남긴다. 비밀값은 코드·로그·커밋에 남기지 않는다(.env). 서버는 0.0.0.0에 바인딩하고 포트는 README를 따른다.

## 검증
- 완료 조건 = ./scripts/check.sh 가 CHECK PASS. 통과하면 코드를 더 고치지 않는다(약속어에 남은 기록·커밋은 마저 하고 멈춘다).
- 과제별 검사는 Codex가 scripts/verify.sh에 직접 쓴다(check.sh가 부른다). "설계"는 3절 검사 계획(무엇을 · 몇 번 구현에서 켬)만 적고, 그 대상을 만드는 "구현"이 verify.sh에 넣고 지금 환경에서 한 번 돌려 본다. 하드 제약 위반만 FAIL, 점수·소프트 제약은 출력만, 바꿀 수 없는 환경 조건(런타임 버전 등)은 경고만, 제출 문서 검사는 SUBMIT=1일 때만.
- 켠 검사를 빼거나 약하게 바꾸려면 먼저 묻는다. 커밋된 테스트의 삭제·skip·기대값 변경도 먼저 묻고, 이유를 Decision Log에 남기고, 따로 커밋한다. 이번 턴에 새로 쓴 테스트의 실수는 근거 1줄을 보고에 적고 고친다.
- 됐다·막혔다는 이번 턴에 실제로 실행한 명령과 그 출력으로만 말한다(7절 근거도 그 출력 원문). 같은 수정이 2번 실패하면 멈추고 7절에 적은 뒤 새 가설을 보고한다.
- CHECK FAIL에 "환경" 줄이 붙고 실패가 EPERM·listen 오류뿐이면 코드를 고치지 말고, check를 샌드박스 밖에서 다시 돌리겠다고 승인을 요청한다.
- 파일을 바꾼 약속어의 끝 보고: 변경 / 검증 명령→결과(통과 수) / 검증 못 한 것 / 사람이 직접 볼 것 1줄(서버를 다시 띄우는 명령 → 미리보기에서 볼 것) / 다음에 칠 약속어 1개. 결과물의 한계는 8절에도 1줄.

## 결정과 커밋
- 요구사항은 R1, R2 …, 줄마다 출처 [README 절] / [담당자 Qn] / [가정: …]. README의 수치·제약·범위 밖은 원문 그대로 옮긴다.
- Decision Log: D-n · 시각 · 결정 · 이유 · 버린 대안. 사람이 정한 것은 "(사람 결정)"을 붙인다. 결정이 바뀌면 옛 줄을 고치지 말고 새 번호로 "D-m 대체".
- 커밋은 완료 조건 하나마다. 첫 줄 "<타입>: <R번호> <무엇을>", 관련 결정이 있으면 끝에 "(D-n)". 태그 r0는 "시작", r1은 "설계 확정"이 단다.
- .git은 샌드박스에서 읽기 전용이다. git 쓰기는 처음부터 샌드박스 밖 실행 승인을 요청하고 한 명령으로 묶는다: `git add <바꾼 파일 경로…> && git commit -m "…"`(태그가 필요하면 `&& git tag <이름>`). git 사용자 이름이 없으면 `git -c user.name=candidate -c user.email=candidate@localhost commit …`.
- 승인 뒤에도 2번 실패하면 더 고치지 말고 커밋 없이 다음 일로 간다: 7절에 에러 원문 1줄, 보고에 사람이 터미널에 그대로 붙일 명령 블록. 커밋·태그 상태는 보고 직전에 `git log --oneline -1` · `git tag`로 확인한 값만 쓴다.

## 약속어
메시지가 아래 형식일 때만 약속어다. 어미는 무시한다("구현해"="구현", "이어서하자"="이어서", "마무리(하자)"="정리"). 약속어 뒤 "— <한 줄>"은 이번 작업의 의도·우선순위로 따르고, 결정이면 D에 "(사람 결정)"으로 남긴다. 담당자의 말을 옮긴 메시지는 "담당자 답"이다. 범위가 없으면 리뷰 = r1..HEAD, 설명 = 마지막 커밋. PLAN.md를 고친 약속어는 끝낼 때 ▶ 두 줄도 고친다. 단계가 여럿인 약속어는 보고 첫 줄에 못 한 단계를 적는다(없으면 "전부 함").

- "시작": r0 태그가 이미 있으면 아무것도 고치지 않고 "이어서"를 한다. 아니면 ① 플랫폼 지침·README·제출 문서 양식을 읽고, 저장소는 `git ls-files` · `git status --short`로 본다 ② 추적 안 된 과제 원본(README·제출 문서 양식·10MB 이하 데이터)을 고치지 않은 채 커밋하고, 키트 파일(AGENTS.md·PLAN.md·scripts/·.gitignore)을 커밋하고 r0를 단다(한 번의 승인으로 묶는다. git 저장소가 없으면 git init 여부부터 묻는다) ③ PLAN.md 1·2절을 채운다. 데이터는 통째로 출력하지 않고 행 수·기간·열·분포·튀는 값·반복되는 패턴을 1절 "데이터 요약" 5줄로 적는다 ④ 담당자 1차 질문 블록("담당자" 형식)을 낸다. 보고: 작업 폴더 / 제출물 / 플랫폼 지침·README와 이 규칙이 부딪히는 곳 / 막힌 것. README가 말하는 작업 폴더가 지금 폴더와 다르면 ② 전에 멈추고 묻는다. 앱 코드는 만들지 않는다.
- "담당자": PLAN.md는 고치지 않는다(보낸 질문은 답을 받을 때 함께 적는다). 1절 데이터 요약·2절 [가정]·10절을 보고 다음에 보낼 질문을 우선순위대로 최대 3개, 한 문장씩 복붙용 블록 하나로 쓰고, 블록 밖에 질문마다 왜 묻는지 1줄. README에 답이 있는 것은 묻지 않는다. 1차 고민 = 가장 큰 불만 · 누가 언제 불편한지 · 결과를 누가 보고 누가 반대하는지 → 2차 기준 = 정해야 할 값("X로 할까요, Y로 할까요?") · 데이터 근거("데이터에 <언제·어디> <쏠림·예외>가 N건 있던데 어떻게 볼까요?") · README 밖 운영 규칙(다음 기간에 달라지는 것 · 이어 쓰거나 연달아 쓸 때의 간격·준비 · 데이터의 반복 패턴이 규칙인지 · 따로 다룰 대상) → 3차 역제안("설계" 뒤) = "이렇게 만들겠습니다: <요약>. 정하기 어려운 <Z>는 옵션으로 두겠습니다(기본값 <V>). 진행해도 될까요?" → 핵심 기능이 돈 뒤 = 결과 숫자로 중간 보고하고 반응을 묻는다.
- "담당자 답: <원문>": 직전에 보낸 질문과 받은 답(내가 직접 되물은 문답 포함)을 원문 그대로 10절에 Qn 한 항목으로 덧붙이고(보낸 질문 · 답 · 반영 · 되물을 것) R·D·옵션에 반영한다. 안 정해진 값은 2절 해당 R에 [가정: …], 정해지면 [담당자 Qn]. README와 다르면 바로 바꾸지 말고 [가정]에 차이를 적고 되묻는다. 미지근한 답 · 수치가 빠진 답 · 남의 말을 전하는 답("…라던데") · 불만·예외를 슬쩍 꺼낸 답 · "먼저"·"신경 써 주세요"처럼 짧은 답은 "되물을 것"에 적는다. 되물을 것이 있으면 다음 질문 블록("담당자" 형식, 되물음 먼저)을, 없으면 다음에 칠 약속어를 낸다. 코드는 고치지 않는다.
- "설계 [확정]": PLAN.md(2절 확인 방법 · 3·4절)만 고치고 멈춘다: 문제 유형 → 접근 2~3개 비교(구현 시간·설명 난이도·제약 충족) → 추천 1개 → 계층 지도 → 구현 순서(번호 목록, 1번은 검증기) → 검사 계획 → 옵션 표 → 용어집(알고리즘 용어도 쉬운 말 1줄). 약 80분 안에 끝낼 크기로 필수부터, 2절 요구사항마다 확인 방법(테스트 이름). "확정"이 붙으면 3절이 마지막 담당자 답과 맞는지 보고 PLAN.md를 커밋하고 r1을 단다(안 맞으면 고칠 곳만 말하고 멈춘다).
- "구현 [번호]": 3절 구현 순서에서 다음 미완 항목 하나(번호를 주면 그것)를 끝에서 끝까지 구현한다. 검사 계획이 이 번호에서 켜라는 검사는 verify.sh에 넣는다. check PASS → 2절 체크 → 11절에 설명 3줄 → 커밋 → 보고 후 멈춘다. 처음으로 끝에서 끝까지 돌면 1절 실행 명령과 README가 요구한 실행 문서도 양식대로 채운다.
- "리뷰 [범위]": 파일을 고치지 않는다. 범위가 "계획"이면 README와 PLAN.md 1~3절을 대조하고(빠진 요구 · 수치 오독 · 모순 · 확인 방법 없음 · 검사 계획이 README 제약을 실제로 막는지) 담당자에게 아직 안 물은 것을 최대 3개 덧붙인다. 그 밖에는 git diff <범위>를 요구사항·계층 경계와 대조한다. 정확성 버그 · 요구사항 누락 · 입력 검증 · 빈 통과하는 검사만, 항목마다 파일:줄 · 실패 시나리오(입력→결과) · P0~P2. 최대 10개, 없으면 "없음".
- "설명 [범위]": 파일을 고치지 않는다. 범위(커밋·파일·R번호·"설계"·"전체")를 비전공자에게 말하듯: 무엇(입력→출력) / 어떻게(핵심 로직 3줄) / 왜(고른 이유·버린 대안, D번호 · 근거가 된 담당자 답 Qn) / 어떻게 검증했나 / 약점·개선점 / 검토자가 물을 만한 질문 2개(답은 쓰지 않는다). "전체"는 한 화면 카드(흐름 · 계층 경계와 파일 · 핵심 결정 5개 · 약점 3개 · 숫자).
- "이해 확인 [개수]": 파일을 고치지 않는다. 처음 본 검토자처럼 구현 로직·선택 이유·계층 경계·검증·개선점을 묻는 질문(기본 5개)을 하나씩 낸다. 답을 먼저 알려 주지 않는다. 내 답을 받으면 코드와 대조해 맞은 것·틀린 것·빠진 것을 파일:줄 근거로 짚고 다음 질문으로 간다.
- "메모: <한 줄>": 5절에 "[메모] 시각 원문"으로 덧붙인다(소감 문서의 재료). 코드는 고치지 않는다.
- "제출 준비": 앱 코드는 고치지 않는다. ① 미완 요구사항·[가정]을 나열하고, 9절(완료 증거 · 한 장 요약)과 README가 요구한 실행 문서를 양식대로 쓰고(실행 방법은 새 터미널에서 그대로 칠 수 있게, 한계와 담당자 재량 옵션 포함) 커밋한다 ② 소감을 묻는 제출 문서는 질문마다 5절 [메모]에서 고른 재료를 보여 주고 내 1~3줄을 기다린다(지어내지 않는다) ③ 답을 받으면 그 뜻대로 쓰고 → `SUBMIT=1 ./scripts/check.sh` → 담당자 완료 보고 3줄 초안(한 것 · 남은 한계를 업무 말로 · 담당자가 바꿀 수 있는 옵션과 바꾸는 법) → 정리.
- "이어서": ./scripts/status.sh 를 실행하고 필요한 절을 읽은 뒤 끝난 것 / ▶ 다음 / 막힌 점을 3줄로 말한다. 기록과 실제(git log·파일)가 다르면 실제가 맞다 — 차이를 말하고 ▶ 두 줄과 2절 체크만 맞춘다. 코드는 고치지 않는다.
- "정리": ▶ 두 줄과 2절 체크를 실제와 맞추고, 5절에 (시각 · 완료+근거 · 다음 · 주의)를 덧붙인 뒤 커밋한다. 보고 맨 위에는 못 채운 완료 조건과 검증 못 한 것(제출 문서가 양식 그대로면 "제출 준비 안 됨")을 둔다.
