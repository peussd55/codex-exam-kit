# 작업 규칙 (짧게 유지한다. 규칙을 하나 더하면 하나를 덜어낸다)

- 과제 README·과제 지침과 이 규칙이 부딪히면 과제가 우선이다. 부딪힌 사실은 Decision Log에 적는다.

## 기록은 PLAN.md 한 곳
- 계획·설계·진행·결정·발견·약점은 PLAN.md에만 쓴다. 코드 주석·커밋·보고에서는 번호(R1, D-1)로 가리키고, 내용을 다시 풀어 쓰지 않는다. 다시 풀어 쓸 때마다 뜻이 조금씩 바뀐다.
- 예외: README가 요구한 제출 문서는 읽는 사람을 위해 문장으로 쓰고, 내용은 PLAN.md에서 가져온다.
- PLAN.md 5절(Progress)·6절(Decision Log)·7절(발견)은 덧붙이기만 하고 지난 줄을 고치지 않는다. 나머지(▶ 두 줄, 1~4절, 8~9절)는 항상 최신 상태로 고친다. 요구사항 체크도 여기에 포함된다.
- 결정·발견은 나온 즉시 적는다. 세션은 언제든 끊길 수 있다.
- 환경·도구에 대해 알게 된 사실(안 되는 것, 실패한 시도, 필요한 옵션)은 7절 발견에 근거와 함께 1줄. 다음 세션이 같은 실수를 하지 않게 하려는 것이다.
- 읽기 전용 세션(보조·리뷰)은 파일을 쓰지 않고 보고만 한다.

## 범위
- 요청과 PLAN.md 요구사항 범위 안에서만 바꾼다. 요청하지 않은 기능·파일·리팩토링·방어 코드는 만들지 않는다.
- 범위 밖에서 발견한 문제는 고치지 말고 8절 알려진 약점에 1줄 적는다.
- 요구사항에 없는 결정이 필요하면 2절의 해당 요구사항 줄에 [가정: …]으로 적고 진행한다.
- 파일 3개 이상을 바꾸거나 구조를 바꿀 때는 먼저 3줄을 말하고 확인을 기다린다: 바꿀 것 / 깨지면 안 되는 것 / 검증 방법. PLAN.md 3절 설계대로 처음 뼈대를 만드는 것은 제외한다.

## 코드
- 새 함수·헬퍼·필드를 만들기 전에 같은 일을 하는 코드가 이미 있는지 검색한다. 이름은 기존 코드와 PLAN.md 용어집을 따른다.
- 판정·계산·검증 로직은 환경변수·DB·네트워크에 의존하지 않는 순수 함수로 두고 단위 테스트한다.
- 한 파일이 400줄을 넘으면 덧붙이지 말고 새 모듈로 나눈다. 기존 파일은 필요한 부분만 고친다.
- 이미 설치된 라이브러리를 먼저 쓴다. 흔한 기반(화면·입력 검증·날짜)을 직접 짜지 말고, 새 의존성이 필요하면 먼저 묻고 이유를 Decision Log에 남긴다.
- 순서·권한·입력 규칙은 서버 코드에서 검사한다. 화면 안내문에만 맡기지 않는다.
- 외부 호출에는 타임아웃을 두고, 실패는 잡아서 로그를 남긴다. 오류를 삼키지 않는다. SQL은 파라미터 바인딩.
- 비밀·개인정보·요청 본문을 통째로 로그에 남기지 않는다. 키는 .env로 두고 커밋하지 않는다.
- 서버는 0.0.0.0에 바인딩한다.

## 검증
- 완료 조건 = ./scripts/check.sh 가 CHECK PASS. 통과하면 멈추고 보고한다.
- scripts/check.sh는 1)·3) 칸에 검사를 더하는 것만 한다. 검사를 빼거나 약하게 바꾸려면 먼저 묻는다.
- 테스트가 실패하면 코드를 고친다. 기존 테스트 삭제·skip·기대값 변경은 먼저 묻고, 이유를 Decision Log에 남기고, 따로 커밋한다.
- 버그를 고칠 때는 재현 테스트부터 만든다. 재현이 안 되면 보고의 '검증 못 한 것' 칸에 이유를 적는다.
- 실행·로그·재현으로 확인한 것만 "됐다"고 말한다. 같은 수정이 2번 실패하면 멈추고, 시도한 것과 결과를 7절 발견에 적은 뒤 새 가설을 보고하고 확인을 기다린다.
- 작업 끝 보고 형식: 변경 / 검증 명령→결과(통과 수) / 검증 못 한 것 / 나중 후보. 검증 못 한 것 중 결과물의 한계는 8절에도 1줄.

## 결정과 커밋
- Decision Log 형식: 한 줄에 결정 하나. D-n · 시각 · 결정 · 이유 · 버린 대안. 결정이 바뀌면 옛 줄을 고치지 말고 새 번호로 "D-m 대체".
- 요구사항 번호는 R1, R2 …, 줄마다 출처 태그를 단다: [README §n] / [담당자] / [가정: …].
- 커밋은 완료 조건 하나마다. 첫 줄 "<타입>: <무엇을>", 관련 결정이 있으면 끝에 "(D-n)". 본문은 왜 1줄 + 검증 1줄. 구조 변경과 동작 변경은 나눠 커밋한다.

## 약속어 (메시지 전체가 정확히 아래 단어일 때만 약속어로 본다)
- "이어서": ./scripts/status.sh 를 실행하고 PLAN.md ▶ 줄·Decision Log·발견을 읽은 뒤, 끝난 것 / ▶ 다음 / 막힌 점을 3줄로 말한다. 코드는 고치지 않는다. 기록과 실제가 다르면 실제가 맞고, 그 차이를 말한다.
- "정리": PLAN.md ▶ 두 줄과 2절 체크를 최신으로 고치고, 5절 Progress에 (시각 · 완료+근거 · 다음 · 주의)를 덧붙인 뒤 커밋한다. 보고 맨 위에는 못 채운 완료 조건과 검증 못 한 것을 둔다.
- "리뷰 <범위>": 파일을 고치지 않는다. PLAN.md 요구사항·완료 조건과 git diff <범위>를 대조한다. 정확성 버그 / 요구사항 누락·위반 / 입력 검증만 본다. 항목마다 파일:줄 · 실패 시나리오(입력→결과) · 심각도 P0~P2. 확신 없는 것과 스타일은 뺀다. 최대 10개, 없으면 "없음".
